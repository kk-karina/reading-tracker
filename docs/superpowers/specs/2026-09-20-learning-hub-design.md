# Learning Hub — дизайн

Дата: 2026-09-20. Статус: на утверждении, редакция 3.

Расширение существующего трекера чтения до личной системы обучения. Ядро трекера
(`books`, `sessions`, `notes`, Полка, Прогресс, Дневник) не переписывается.

**К реализации предлагается только §0 «Итерация 1».** Всё остальное — горизонт:
проектирование доведено далеко вперёд, потому что дальние решения определяют форму
модели данных уже сейчас. Каждая следующая ступень надстраивается и ничего из
сделанного не переписывает.

| Ступень | Что добавляет | Новых сервисов |
|---|---|---|
| **Итерация 1** — сейчас | Категории, материалы, конспекты. Всё вручную, `localStorage` | **ноль** |
| Дальше | Сессии, ритм, «Следующее действие», захват, глобальный дашборд | ноль |
| Уровень 1 | Obsidian | Supabase, локальный агент |
| Уровень 2 | Уведомления | macOS: агент уже есть · почта: +4 |

Уровень 1 вынужден не почтой, а агентом: **агент не может писать в `localStorage`
браузера**, и место, куда он складывает прочитанное из Obsidian, может быть только
базой.


## 0. Итерация 1 — что делается сейчас

Уточнено 2026-09-21. **Всё, что ниже раздела 1, — горизонт**: там спроектированы
потоки, сессии, ритм, напоминания, Obsidian и уровни 1–2. К реализации сейчас
предлагается только этот раздел. Остальное надстраивается итерациями и ничего
из сделанного не переписывает.

Всё вводится вручную, ничего ниоткуда не переносится, новых сервисов ноль,
хранилище — `localStorage`, как у трекера чтения.

### Структура

```
Обучение
└── Категория — таб: Professional Growth · Driving · English · [+]
    └── Материал — книга · статья · курс · видео · другое
        └── Конспект — markdown, теги, выделение главного
```

«Входящие» не отдельный раздел, а статус материала. Конспект не существует сам по
себе — он всегда внутри материала.

### Данные

Три сущности в `localStorage`, за интерфейсом `LearningStore` — тем же приёмом, что
`DataStore` в ядре, поэтому будущий переход на базу не тронет ни один экран.

```ts
interface LearningCategory {
  id: string
  name: string                  // переименовывается свободно
  icon: IconName
  accent: string | null         // из проверенного набора, не пипеткой
  outline: string | null        // markdown-скелет нового конспекта этой категории
  sort: number
  archived: boolean
  created_at, updated_at
}

interface Material {
  id: string
  category_id: string
  title: string
  kind: 'book' | 'article' | 'course' | 'video' | 'podcast' | 'other'
  author: string | null
  url: string | null
  status: 'inbox' | 'active' | 'done' | 'reference' | 'dropped'
  parts_total: number | null    // 41 глава; для статьи пусто
  sort: number
  created_at, updated_at
}

interface StudyNote {           // конспект
  id: string
  material_id: string
  part: string | null           // «Глава 1. Nobody Thinks Like You»
  title: string | null
  body: string                  // markdown, включая ==выделение==
  tags: NoteTag[]               // та же пятёрка, что у мыслей о книгах
  date: string                  // YYYY-MM-DD
  sort: number
  created_at, updated_at
}
```

Заметны три решения.

**Конспект — на главу, а не на материал.** Так вы уже пишете в Obsidian: в `Weekly/`
запись на главу. Отсюда же берётся прогресс: **глава считается пройденной, когда по
ней есть конспект.** Отдельной галочки «прочитано» нет намеренно — потребление и
обучение это не одно и то же, и модель не должна делать вид, что одно. У статьи
конспект обычно один, и это частный случай, а не второй вид материала.

**Теги на весь конспект, и их несколько.** У мысли о книге тег ровно один и выбирается
первым, потому что он задаёт рамку короткой записи. Конспект длинный и может нести
и цитату, и вопрос сразу, поэтому здесь это массив чипсов в шапке листа. Словарь тот
же — цитата, идея, вопрос, несогласие, ощущение, — так что переводы и стили уже есть.

**Контур живёт на категории, а не на конспекте.** Поле `outline` — markdown-скелет,
который подставляется в новый конспект этой категории. У Professional Growth это
«Главное / Моя поправка / Вопрос / Синтез / Применение», у Driving своё. Обязательных
полей формы нет: жёсткие секции наказывают конспект, который в них не лезет, а контур
даёт структуру бесплатно и стирается как обычный текст. Это же одним полем закрывает
«разным потокам нужны разные вещи» — без системы модулей.

### Экраны

**`/learning`** — табы категорий, под ними материалы активной категории: название,
вид, автор, статус, прогресс «2 из 41». Кнопки «+ Материал» и «+ Категория».

**`/learning/m/:id`** — материал: шапка со статусом и прогрессом, под ней стопка
конспектов по главам, «+ Конспект». Для статьи стопка из одного.

**`/learning/n/:id`** — конспект листом A3. Читается по умолчанию, правится по кнопке.
Клик по тексту в поле ввода не превращается: в этом проекте всё явное.

Хлебные крошки как на странице книги: `← Professional Growth` и `← Материал`.

### Лист

Продолжение `.thought-card`, а не новая поверхность: та же тёплая бумага, тот же свет
из верхнего левого угла, то же внутреннее кольцо и мягкая тень — но крупно. Поля
48–56px, кегль 16–17px, интерлиньяж 1.7, строка до ~70 знаков, слева тонкая линия
поля как в тетради.

**От A3 берётся ощущение, а не пропорции.** Буквальные 1:1.41 дают фиксированную
высоту, текст в неё не влезает, и получается прокрутка внутри прокрутки — худшее для
чтения. Высота по содержанию: лист растёт вниз, как страница, на которой продолжают
писать.

### Разметка

Свой рендерер markdown, ~120 строк, покрыт тестами. Прецедент в проекте есть:
локализация написана своя, без библиотеки, и себя оправдала. Markdown — то, на чём
говорит Obsidian, поэтому на следующих итерациях ничего не придётся конвертировать.

Поддерживается: `#`–`###`, `**жирный**`, `*курсив*`, `` `код` ``, списки `-` и `1.`,
цитата `>`, линия `---`, ссылка `[текст](url)`, абзацы по пустой строке. HTML
экранируется, наружу идут только известные теги.

**Текстовыделитель — `==главное==`.** Родная разметка Obsidian, переживает копирование
и чтение файла глазами, и не требует нового цвета: `--brand: #e9f86b` — это буквально
лимонный маркер, акцент системы и есть выделитель. В редакторе — выделить мышью и
`Cmd+H` или кнопка. Один цвет, не палитра: несколько Obsidian не поймёт, а через месяц
никто не вспомнит, что означал зелёный.

### Что переиспользуется

`Sheet` для форм, `Segmented` для статуса, `.chips` для тегов, `.crumbs` для крошек,
`Jelly`, `listItem`, `Icon`, бумажный словарь `.thought-card`, `fmtDate` с локалью и
множественными числами, паттерн `DataStore`.

### Что пишется

`lib/learning/types.ts`, `lib/learning/store/{types,local}.ts`,
`lib/learning/markdown.ts` + тест, `state/LearningContext.tsx`,
`pages/{Learning,Material,StudyNote}.tsx`,
`components/{MaterialForm,CategoryForm,NoteEditor}.tsx`, секция в `index.css`,
ключи словаря, пятый пункт в `Shell.tsx`.

### Тесты

Только то, что ломается тихо: рендерер markdown (включая экранирование HTML и
`==выделение==`) и `localLearning`. Интерфейс не покрывается — правило ядра.

### Чего в этой итерации нет

Сессий, ритма, «Следующего действия», напоминаний, режима возврата, глобального
дашборда обучения, захвата снаружи, Supabase, Obsidian, агента, писем, миграции
данных. Всё это спроектировано ниже и добавляется итерациями.

## 1. Что это и зачем

Проблема не в нехватке материалов. Проблемы такие:

1. Сохранённое забывается.
2. Системы обучения заводятся и бросаются.
3. Профессиональный опыт ощущается как ноль, хотя он есть.
4. Нужна видимая непрерывность и накопленное свидетельство.
5. Захват должен стоить меньше усилия, чем решение не захватывать.
6. Напоминания в календаре и в ChatGPT игнорируются.
7. Ещё одна система, требующая обслуживания, не нужна.

Отсюда три вещи, которые Hub обязан делать, и по которым его судят:

- **Одно очевидное следующее действие** на каждом экране потока. Сессия не должна
  начинаться с выбора.
- **Непрерывность вместо серий.** «Активна 6 из последних 8 недель», а не «42 дня
  подряд». Пропуск недели не наказывается ничем, а возвращение после месяца
  отсутствия — отдельный, спроектированный случай, а не стена пропусков.
- **Применение видно наравне с потреблением.** Прочитанное без применённого —
  не обучение, и дашборд не должен делать вид, что это одно и то же.

Пункт 7 — не пожелание, а критерий отбраковки. Каждое решение ниже, создающее второе
место для одних и тех же данных, обязано либо назвать владельца, либо быть отвергнутым.

## 2. Ключевые решения

| Решение | Основание |
|---|---|
| Поток — настраиваемая сущность, Professional Growth ничем не выделен в схеме | Проверка на хардкод: Driving и English заводятся в MVP пустыми. Если для них приходится трогать код — модель неверна |
| Отдельный `LearningContext`, но общий с ядром механизм оптимистичных мутаций | `DataContext.run()` перезагружает весь снимок после каждой мутации. В localStorage это стоило ноль, по сети — сотни миллисекунд на каждое нажатие. Два разных механизма в одном проекте разойдутся, поэтому оптимистичность выносится в общий хелпер и применяется к обоим |
| `learning_item.book_id` — мост к Полке | Книга остаётся книгой; прогресс подтягивается из уже оттестированной `lib/reading.ts`. Ни строки в чтении не меняется |
| **Уровень 0 остаётся на `localStorage`** | Supabase был вынужден почтой и агентом. Без них он не нужен, а его включение отнимает офлайн и замедляет запись (см. §9). Хранилище прячется за интерфейсом `LearningStore` — ровно как `DataStore` в ядре, — поэтому переход на базу на Уровне 1 будет сменой одной строки, а не переписыванием |
| Кэш снимка на чтение — задача Уровня 1 | На Уровне 0 данные и так локальные, кэшировать нечего. Проектируется заранее, чтобы включение базы не отняло офлайн |
| **`next_action` — поле, а не вывод; заполняется в конце сессии** | Вывести «Главу 3» из свободного текста «Глава 2» нельзя, а структурный прогресс не описывает «20 вопросов теории» и «15 минут условных предложений». Один вопрос в конце сессии даёт точную формулировку от того, у кого контекст ещё в голове, и переносит решение из начала сессии, где оно дорого, в конец, где почти бесплатно |
| *(Уровень 2)* Напоминания — письмом, не браузером | Браузер не умеет разбудить при закрытой вкладке без облачного push. Почта переживает закрытый ноутбук и приходит на телефон |
| *(Уровень 2)* **Планировщик — GitHub Actions, логика — догоняющая** | Бесплатный Supabase засыпает после 7 дней без внешних запросов, и `pg_cron` паузу не предотвращает: механизм возврата отключался бы условием «вы не возвращались». Внешний вызов и будит проект, и рассылает. Но планировщик GitHub задерживается и под нагрузкой пропускает запуск молча — поэтому функция обрабатывает всё, что стало должным с момента последней отправки, а не текущий слот |
| *(Уровень 2)* **Действия из письма выполняются по нажатию, не по переходу** | Корпоративные сканеры ссылок (Safe Links и подобные) делают GET по каждой ссылке в письме до того, как его откроют. GET-ссылка «Сделала» помечала бы выполненным каждое напоминание в момент доставки, и статистика врала бы в приятную сторону |
| *(Уровень 2)* Письмо на каждое напоминание, не дайджест | Сила письма — в том, что оно приходит в момент действия и содержит ровно одно действие |
| *(Уровень 1)* **Мост с Obsidian — локальный агент по расписанию, не браузер** | Страница на GitHub Pages не имеет расписания: File System Access API работает только пока вкладка открыта в Chrome, то есть «раз в день» недостижимо в принципе. Агент на Node под `launchd` читает vault напрямую, работает при закрытом браузере и делает Hub одинаковым в Safari и с телефона |
| Две реализации синхронизации не держим | FSA и агент делали бы одно и то же двумя путями. В личном проекте они разойдутся, а каждая лишняя дорога к записи в vault — лишнее место, где можно испортить заметку |
| *(Уровень 1)* **База владеет записью инсайта, vault — его текстом** | Инсайт нужен в базе ради даты, потока, тегов и связи с применением, и должен создаваться во Фазе 1, когда vault ещё не подключён, и в Safari, где его не будет. Текст правится в Obsidian и при конфликте выигрывает |
| **Бэклог живёт в Hub, `Inbox.md` — генерируемое зеркало** | «Общее владение» — это отсутствие решения и прямой путь к обслуживанию двух систем. Статусы меняются в одном месте |
| Синхронизация с vault — сначала только чтение | Чтение даёт главную ценность (ChatGPT записал → Hub показал) при нулевом риске. Запись включается отдельно |
| Приложение никогда не переписывает тело заметки | Три разрешённые операции и никаких других |
| Производные величины не хранятся | Правило ядра (`lib/reading.ts`). Новый `lib/learning/metrics.ts`, покрытый тестами |
| Пятый пункт меню, плоская навигация | Принято по умолчанию. Группировка в два уровня — отдельное решение после реального использования |
| Applied / Practiced входит в MVP | В исходном списке MVP его не было. Без него дашборд снова меряет только потребление |

## 3. Информационная архитектура

```
Прогресс · Полка · Дневник · Обучение · Настройки     [+ Захват]  [РУ|EN]
                              ↑ новое                   ↑ новое, всегда виден, клавиша C

/learning                  глобальный дашборд
/learning/inbox            входящие: разбор захваченного
/learning/:slug            дашборд потока
/learning/:slug/backlog    бэклог потока
/capture?url=…&title=…     точка захвата снаружи: закладка браузера, Shortcut на iPhone
/r/:token                  (Уровень 2) страница действий из письма
```

Чтение потоком не становится. Полка, Прогресс и Дневник остаются как есть.

## 4. Модель данных

**На Уровне 0 всё это живёт в `localStorage`** — той же формой, тем же набором полей,
за интерфейсом `LearningStore`. SQL ниже пишется сразу и не применяется: модель
в виде схемы перестаёт быть словами, а Уровень 1 становится «вставить и нажать Run».

Паттерн ядра сохраняется: `user_id` с дефолтом `auth.uid()`, RLS `for all using
(auth.uid() = user_id) with check (auth.uid() = user_id)` на каждой таблице.
Файл `supabase/migrations/003_learning.sql`.

Уровень 0 использует: `streams`, `learning_items`, `learning_sessions`, `insights`,
`applications`, `reminders`, `reminder_events`. Таблицы `reminder_deliveries` и
`profiles` относятся к Уровню 2 и на Уровне 0 не создаются.

```sql
create table if not exists public.streams (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  -- slug задаётся один раз и не меняется: это ключ связи с vault.
  -- Переименование потока меняет name, не slug.
  slug text not null,
  name text not null,
  icon text not null default 'compass',
  -- Акцент выбирается из проверенного набора, а не пипеткой: правило ядра
  -- «всё тонкое рисуется чернилами, акцент живёт только в крупных заливках»
  -- свободная палитра отменяет.
  accent text check (accent in ('lemon','sage','clay','slate','plum','sky','sand','rose')),
  focus text,
  intention text,
  -- Формулируется в конце сессии, показывается на дашборде и в теме письма.
  next_action text,
  next_action_minutes integer check (next_action_minutes > 0),
  status text not null default 'active' check (status in ('active','archived')),
  modules text[] not null default '{}',
  read_soon_limit integer,
  vault_path text,
  sort integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, slug)
);

create table if not exists public.learning_items (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  stream_id uuid references public.streams(id) on delete set null,  -- null = не разобрано
  title text not null,
  url text,
  body text,
  source_type text not null default 'other' check (source_type in
    ('article','book','course','video','podcast','idea','insight','question','other')),
  status text not null default 'inbox' check (status in
    ('inbox','read-soon','reference','someday','active','done','dropped')),
  topic text,
  effort_min integer check (effort_min > 0),
  priority smallint check (priority between 1 and 3),
  book_id uuid references public.books(id) on delete set null,
  progress_note text,
  -- Кэш пути. Авторитетен id во frontmatter: переименование заметки в Obsidian
  -- чинится сканированием, а не ломает связь.
  vault_ref text,
  sort integer not null default 0,
  -- Надгробие вместо удаления: иначе файл в vault воскресит удалённый элемент
  -- при следующем чтении.
  deleted_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint learning_items_has_content check (url is not null or body is not null)
);

-- Один активный материал на поток — тот же приём, что books_one_focus в ядре.
-- Без него «Следующее действие» выбирает произвольно.
create unique index if not exists learning_items_one_active
  on public.learning_items (stream_id) where status = 'active' and deleted_at is null;

-- Тот же приём, что external_id у книг: одна и та же статья не заводится дважды.
create unique index if not exists learning_items_url_once
  on public.learning_items (user_id, url) where url is not null and deleted_at is null;

create table if not exists public.learning_sessions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  stream_id uuid not null references public.streams(id) on delete cascade,
  date date not null,

-- триггером, а не надеждой на то, что интерфейс её когда-нибудь запишет.
create or replace function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  insert into public.profiles (user_id) values (new.id) on conflict do nothing;
  return new;
end;
$$;

drop trigger if exists on_auth_user_created on auth.users;
create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

## 5. Производные величины

Не хранятся, считаются на лету. `src/lib/learning/metrics.ts`, покрыт тестами.

| Величина | Как |
|---|---|
| Сессий и минут за неделю | фильтр `learning_sessions` по дате |
| **Активных недель из 8** | недель с ≥1 сессией за последние 8 календарных недель |
| Тепловая карта ритма | обобщённый `Rhythm` по минутам вместо страниц |
| **Следующее действие** | `stream.next_action`, если заполнено; иначе первый `read-soon` по `sort`; иначе ближайшее напоминание; иначе «выбрать материал» |
| Пропущенные сессии | `reminders` без `reminder_events` **за последние 7 дней**; старшее гасится молча |
| Счётчик Входящих | `learning_items` со `stream_id is null` или `status = 'inbox'` |
| Прогресс по книге | `progressOf()` из существующей `lib/reading.ts`, если задан `book_id` |
| **Режим возврата** | перерыв больше 14 дней без сессий → дашборд переключается, см. §6 |

Тестами покрывается то, что ломается тихо: `activeWeeks` на границе недели и года,
`nextOccurrence` напоминания через переход на летнее время и через воскресенье как
день 0, `nextAction` при пустом бэклоге, порог режима возврата.

## 6. Экраны

Во всех новых экранах пустое состояние проектируется наравне с заполненным — правило
ядра, выведенное там на опыте: экран со словом «Скоро» читается не как «данных пока
нет», а как дырка в продукте. Первый запуск без единого потока — отдельный экран с
одним действием «Создать поток», а не пустая сетка.

Доступность держится на том же уровне, что в ядре: `:focus-visible` везде,
`role="radiogroup"` у сегментов, `aria-modal` у листов, вкладки бэклога — настоящие
`tab`/`tabpanel`.

### `/learning` — глобальный дашборд

Порядок блоков сверху вниз отличается от исходного списка намеренно: **Ближайшее
идёт первым**. Главная жалоба — «я пропускаю напоминания»; блок, который нельзя
пропустить, не может стоять четвёртым.

```
Среда, 23 сентября · 19:00                          [ Начать ]
Professional Growth · 20–30 мин
Продолжить Product Design Psychology — Глава 3
─────────────────────────────────────────────────────────────
Пропущено: воскресенье · Разбор Входящих   [Сделала] [Пропустить]

ТЕКУЩИЕ ПОТОКИ        карточки активных потоков
  имя · текущий фокус · текущий материал · прогресс · последняя активность ·
  следующая сессия · «этот месяц: 4 сессии / 145 мин»

ЭТА НЕДЕЛЯ            компактно, компонент stat-row
  3 сессии · 95 мин · 2 потока · 4 инсайта · 1 применение
  Активна 6 из последних 8 недель

ВХОДЯЩИЕ 7 →          ПОСЛЕДНИЕ ИНСАЙТЫ  (thought-card, существующий)
```

### Режим возврата

Вся система существует ради того, чтобы пережить провал, поэтому возвращение после
перерыва — спроектированный экран, а не побочный эффект. При перерыве больше 14 дней:

```
С возвращением.
Вы остановились на Product Design Psychology — Глава 3.

                                              [ Продолжить ]
```

Ни одного пропуска, ни одного счётчика, ни слова о том, сколько времени прошло.
«Активна N из 8 недель» в этом режиме не показывается: в момент возврата это не
сведение, а обвинение.

### `/learning/:slug` — дашборд потока

«Следующее действие» — самый крупный элемент после шапки: одна строка, одна кнопка,
никакого выбора.

```
Professional Growth
Фокус: Product Design Psychology
Цель: вернуть уверенность в профессиональном суждении

┌─ СЛЕДУЮЩЕЕ ДЕЙСТВИЕ ────────────────────────────────┐
│  Прочитать Главу 3 — ~20 мин          [ Начать ]    │
└─────────────────────────────────────────────────────┘

ТЕКУЩИЙ ФОКУС   материал · прогресс («2 главы») · следующее
РИТМ            тепловая карта · «Активна 6 из 8 недель» · 4 сессии · 145 мин
БЭКЛОГ          [ Входящие 3 · Read Soon 4/5 · Справка · Когда-нибудь ]
ИНСАЙТЫ         ПРИМЕНЕНО
```

Лимит Read Soon показывается как «4/5»; превышение — мягкая подсказка, не запрет.
Архивированный поток доступен по ссылке, но не показывается на глобальном дашборде
и не шлёт писем.

### Лист сессии

Поля: поток, дата, минуты, материал, заметка, «+ инсайт», «+ применение». И один
обязательный вопрос в конце — **«Что дальше?»** с подстановкой предыдущего значения.
Это единственное обязательное поле во всей системе, и оно обязательно потому, что
оплачивает собой весь следующий заход.

### Лист захвата

```
[Статья][Книга][Курс][Видео][Подкаст][Идея][Инсайт][Вопрос][Другое]

Ссылка или текст
┌──────────────────────────────────────────┐
└──────────────────────────────────────────┘

▸ Подробнее        (поток, тема, оценка времени, приоритет — свёрнуто)
                                        [ Сохранить ]
```

Поток не спрашивается. Статус по умолчанию `inbox`. Ссылка, которая уже есть в
бэклоге, не создаёт дубль, а открывает существующий элемент.

Тот же лист открывается роутом `/capture?url=…&title=…` — это делает возможными
закладку в браузере и Shortcut из меню «Поделиться» на телефоне, то есть захват без
открытия приложения. Без этого «крайне низкое трение» означает «открой приложение и
нажми C», что трением как раз и является.

## 7. Ритм и напоминания

**Уровень 0 — только внутри приложения.** Таблицы `reminders` и `reminder_events`
живут с первого дня: они описывают ваш ритм (среда 19:00, суббота утром) и хранят
«сделала / отложила / пропустила». Их читает блок «Ближайшее / Пропущено» на
дашборде — самый заметный элемент экрана, потому что главная жалоба в том, что
напоминания проходят мимо.

Исчезает на Уровне 0 только **канал доставки наружу**, а не замысел. Поэтому
уведомления потом добавляются без единой миграции: появляется тот, кто отправляет,
и всё.

Ниже — устройство почтового канала. Это Уровень 2, к реализации сейчас не
предлагается, но записано, потому что определяет пару полей в модели.

### Почтовый канал *(Уровень 2)*

```
GitHub Actions, cron '7,37 * * * *'     нечётные минуты: пик нагрузки приходится
        │                                на начало часа и границы */5
        ▼
POST  $SUPABASE_URL/functions/v1/remind
        │  внешний запрос будит проект: бесплатный Supabase засыпает
        │  после 7 дней без обращений, и pg_cron паузу не предотвращает
        ▼
Edge Function «remind»
        ├ берёт всё, что стало должным с момента последней записи в
        │  reminder_deliveries — а не то, что должно прямо сейчас
        ├ отбрасывает уже отправленное по (reminder_id, due_at)
        ├ учитывает snoozed_until и archived-потоки
        ├ собирает конкретику: stream.next_action + next_action_minutes
        └ Resend → письмо, отметка в reminder_deliveries
```

Догоняющая логика — не оптимизация, а ответ на свойство любого бесплатного
планировщика: GitHub задерживает запуск на 5–20 минут штатно и под нагрузкой
пропускает его молча, без ошибки и уведомления. Слотовая логика теряла бы письмо
навсегда; догоняющая превращает пропуск в опоздание.

**Точность — не лучше получаса.** «Среда 19:00» приезжает между 19:07 и 19:45. Для
«среда, вечером» это несущественно, и записано здесь, чтобы потом не выглядеть багом.

**GitHub отключает запланированные workflow после 60 дней без активности в
репозитории.** Это больше, чем недельный порог Supabase, но меньше, чем возможный
перерыв. Лечится коммитом раз в пару месяцев; Настройки показывают дату последней
успешной отправки, так что молчание заметно.

### Письмо

```
Тема:  Professional Growth · 20 мин — Глава 3
Тело:  Продолжить Product Design Psychology — Глава 3
       [ Сделала ]   [ Отложить на завтра ]   [ Пропустить ]
```

- Тема содержит действие. «Time to learn!» не отправляется никогда.
- **Кнопки ведут на `/#/r/:token`, где действие выполняется по нажатию.** Корпоративные
  сканеры ссылок делают GET по каждой ссылке до того, как письмо открыто; GET-ссылка
  «Сделала» помечала бы выполненным каждое напоминание в момент доставки.
- Токен — HMAC на секрете Supabase, срок 7 дней, одноразовый, несёт только
  `reminder_id` и `due_at`.
- Язык письма берётся из `profiles.locale`. Шаблоны живут в модуле, который
  импортируют и фронтенд, и Edge Function: две копии текста разойдутся за месяц, и
  правило ядра «пропущенный перевод роняет `tsc`» на серверную копию не действует.
- Пропуск не ломает ничего и не порождает ни одного упрёка. Отсутствие формулировок
  вины проверяется при ревью словаря, а не на глаз.

### Доставляемость и наблюдаемость

Ключ Resend лежит в секретах Supabase и во фронтенд не попадает. Бесплатный тариф —
100 писем в день; при трёх потоках расход 5–8 в неделю.

Получатель — личная Gmail, а не корпоративный ящик, и это заметно снижает риск: Gmail
терпимее к общим доменам, чем корпоративный фильтр, и не имеет сканера ссылок,
нажимающего кнопки за вас. Кнопки всё равно остаются на нажатие, а не на переход:
одна лишняя кнопка против целого класса тихой порчи данных.

Одно жёсткое условие. Общий песочный домен `onboarding@resend.dev` шлёт **только на
адрес, на который зарегистрирован аккаунт Resend**. Значит, аккаунт Resend
регистрируется на ту же Gmail, которой выполняется вход в приложение. Отдельного поля
для адреса получателя в модели нет и не нужно: источник один — `auth.users.email`.
Второй адрес потребовал бы верификации своего домена через DNS.

Поэтому письмо не единственный носитель:

- при настройке отправляется проверочное письмо, а не «настроили и надеемся»;
- Настройки показывают журнал `reminder_deliveries`: когда отправлено, с какой
  ошибкой, когда была последняя успешная отправка;
- если за две недели ни одного взаимодействия из почты при отправленных письмах,
  Hub при открытии говорит прямо: «письма, похоже, не доходят»;
- у функции есть режим сухого прогона: она единственная работает без присмотра, и
  её отказ иначе обнаруживается тем, что чего-то *не* пришло.

## 8. Obsidian *(Уровень 1)*

### Мост — локальный агент, а не браузер

Страница на GitHub Pages не имеет расписания. File System Access API работает только
пока вкладка открыта в Chrome с выданным разрешением, поэтому «сравнивать раз в час»
через браузер недостижимо в принципе: нет вкладки — нет процесса, который что-то
сравнит. FSA из проекта исключается.

Мостом становится маленький агент на Node в том же репозитории, запускаемый `launchd`
раз в час:

```
launchd, ежечасно
      ▼
npm run sync
      ├ читает vault напрямую: полный доступ к файлам, без разрешений браузера
      ├ сравнивает с Supabase по id из frontmatter и по хешу тела
      ├ новое и изменённое в Obsidian → в базу
      └ то, чем владеет Hub → обратно в vault (Фаза 3)
```

Что это даёт помимо расписания:

| Было бы с FSA | С агентом |
|---|---|
| Только Chrome, Edge, Arc, только десктоп | Браузер не участвует вообще |
| В Safari и с телефона vault недоступен | Доступен: знание уже в базе к моменту, когда вы открыли Hub |
| Разрешение на папку, пусть и постоянное | Не требуется |
| Синхронизация только при открытии Hub | По расписанию, при закрытом браузере |
| Кодек Markdown тестируется через браузерный API | Тестируется обычным `vitest` на временной директории |

Побочно агент ежечасно обращается к Supabase и служит вторым контуром против
недельной паузы. Основным он быть не может: при выключенном Mac не работает ни он,
ни синхронизация. Первый контур — GitHub Actions, см. §7.

**Ограничение, которое надо принять.** Агент живёт на одном Mac. Mac выключен —
синхронизации нет. Путь к vault изменился — агент останавливается молча. Поэтому
`profiles.vault_synced_at` пишется при каждом успешном прогоне, а Настройки
показывают дату последней синхронизации рядом с датой последней отправки письма:
обе части системы работают без присмотра, и обе обязаны быть наблюдаемыми.

### Работа под iCloud

Vault лежит в `~/Documents`, а `~/Documents` синхронизируется с iCloud Drive: папка
видна и по локальному пути, и под `~/Library/Mobile Documents/com~apple~CloudDocs/`.
Это осознанное решение — iCloud закрывает отказ Mac. Но он синхронизация, а не
резервная копия: удаление и порчу он разнесёт по всем устройствам. Поэтому два
механизма под два разных отказа, и агент обязан вести себя соответственно.

1. **Ничего не удалять. Никогда.** Удаление файла расходится через iCloud мгновенно и
   необратимо. Удалённый в Hub элемент получает `deleted_at` в базе; заметка остаётся
   лежать. Единственная по-настоящему невосстановимая операция просто отсутствует.
2. **Запись атомарная.** Временный файл в `~/.local/state/learning-hub/tmp/` и
   `rename()` на место. Домашний каталог и iCloud-папка — один том APFS, поэтому
   переименование атомарно, и iCloud никогда не видит наполовину записанный файл.
   Открыть существующую заметку на запись и переписать — запрещено.
3. **Резервная копия до первого изменения** каждого файла, в
   `~/.local/state/learning-hub/backups/<дата>/`. Вне `~/Documents`, то есть **вне
   iCloud**: копия, которая синхронизируется вместе с оригиналом, не защищает от
   плохой записи. Хранятся markdown, объём копеечный.
4. **Конфликтные копии — стоп, а не догадка.** Увидев рядом `Inbox 2.md` или иную
   копию, созданную iCloud, агент прекращает работу с этим файлом и сообщает. Выбирать
   победителя за пользователя он не имеет права.
5. **Выгруженные файлы не скачиваются.** Файл без содержимого (`.icloud`-заглушка)
   пропускается с отметкой, а не материализуется: при включённом «Оптимизировать
   хранилище» обход иначе потянул бы гигабайты.
6. **Читать часто, писать редко.** Чтение раз в час безопасно и не создаёт нагрузки на
   синхронизацию. Запись — не чаще раза в сутки и только если сгенерированный блок
   действительно отличается от лежащего на диске.
7. **Повторная сверка перед самым `rename`.** `mtime` и размер проверяются ещё раз
   непосредственно перед подменой. Гонку с демоном iCloud это не устраняет полностью,
   но сужает до миллисекунд, а пункты 1–3 делают её последствия обратимыми.

Приятное следствие порядка фаз: **до Фазы 3 агент вообще не пишет.** Фазы 1 и 2
работают только на чтение, так что поведение iCloud будет изучено на безопасных
операциях раньше, чем появится первая запись.

### Границы и зависимости

```
Корень работы:     Education/Professional Growth   (из конфига, не из базы)
За корень:         не выходит; симлинки наружу не разыменовывает
Точечные папки:    не читает  (.obsidian, .claude — внутри vault их пять)
node_modules:      не читает  (внутри vault их 461, и 2933 чужих .md)
Вложения, бинарь:  не трогает
```

Ограничение корня — не оптимизация. Во всём vault 3114 файлов `.md`, из них
относящихся к делу 181; слепой обход был бы медленным, бессмысленным и при выгруженных
файлах разрушительным.

**У агента ноль внешних зависимостей — только стандартная библиотека Node.** Он
запускается раз в час с полными правами пользователя; каждая зависимость из npm — это
чужой код, исполняемый ежечасно на вашей машине. Для чтения markdown и запроса по HTTPS
стандартной библиотеки достаточно, поэтому это не аскеза, а отказ от лишнего риска.

**Учётные данные лежат вне vault и вне iCloud:** `~/.config/learning-hub/`, права `600`.
Токен внутри `~/Documents` уехал бы в облако вместе с заметками.

### Доступ к данным

Агент входит под тем же аккаунтом один раз; refresh-токен лежит локально в файле с
правами `600`. **`service_role` не используется** — RLS продолжает действовать, и
утечка локального файла не даёт больше, чем даёт доступ к самому Mac.

### Слои

```
Браузер:   Экран  ──►  LearningContext  ──►  Supabase (+ кэш снимка)

Mac:       launchd ──► sync ──► VaultAdapter (fs) ──► Markdown
                                     │
                                MarkdownCodec  (frontmatter ⇄ объект)
                                     │
                                  Supabase
```

Фронтенд не знает о файловой системе ничего и никогда с ней не разговаривает.
`VaultAdapter` и `MarkdownCodec` живут в агенте; общими с приложением остаются только
типы и правила разбора frontmatter.

### Кто чем владеет

| Данные | Владелец | Разрешение конфликта |
|---|---|---|
| Инсайт: запись (дата, поток, теги, связи) | база | база |
| Инсайт: текст | Obsidian | **файл выигрывает**; `body_hash` показывает, что текст изменился снаружи |
| Principles, Evidence, Weekly, Sources | Obsidian | файл; агент создаёт только новые |
| **Бэклог (элементы и статусы)** | **Hub** | база; `Inbox.md` перегенерируется между маркерами |
| Learning sessions | Hub | база; в vault дозаписываются в `Weekly/YYYY-Www.md` |
| Streams, reminders, язык, свёрнутые блоки, фильтры | только Hub | в vault не попадает никогда |

Следствие, которое надо знать заранее: **правка статуса руками в `Inbox.md` не
вернётся в Hub** — она будет затёрта при следующей перегенерации блока между
маркерами. Это цена одного владельца и отказа от обслуживания двух систем.

`vault_ref` — кэш пути, а не связь. Авторитетен `id` во frontmatter: переименование
заметки в Obsidian чинится сканированием и обновлением пути, а не рвёт связь.

### Правила записи

Записывает только агент, и только так:

1. Разрешены ровно три операции: создать новый файл; перезаписать блок frontmatter;
   дописать между маркерами `<!-- learning-hub:start -->` и `<!-- learning-hub:end -->`.
   Тело заметки вне маркеров не изменяется никогда.
2. Перед записью — сверка `mtime` и хеша с тем, что было прочитано. Не совпало →
   **запись не выполняется, конфликт попадает в базу и показывается в Hub**.
3. Собственные записи помечаются хешем, иначе агент примет свою правку за внешнюю и
   войдёт в петлю «записал → увидел изменение → перечитал».
4. Удаление — всегда `deleted_at`, никогда не жёсткое: иначе оставшийся файл воскресит
   элемент при следующем чтении.
5. Существующие заметки получают frontmatter **только после явного подтверждения**.
   Агент сам ничего не мигрирует: он печатает дифф и ждёт `npm run sync -- --adopt`.
6. У агента есть `--dry-run`, и в Фазах 1–2 он запускается только так.

### Frontmatter

```yaml
---
type: learning-item        # learning-item | insight | session | principle | evidence | uncertainty | source
id: lh-01J8Z...            # авторитетная связь; путь файла — лишь кэш
stream: professional-growth
status: read-soon
source_type: article
topic: product-design-psychology
url: https://...
effort_min: 25
created: 2026-09-20
updated: 2026-09-20
---
```

```yaml
---
type: insight
id: lh-01J8Z...
stream: professional-growth
topic: product-design-psychology
source: PG-002 — Product Design Psychology
tags: [evidence, expert-judgment]
changed_my_mind: true
created: 2026-09-20
---
```

**Инсайт не обязан быть отдельным файлом.** Проверка на реальном vault показала, что
инсайт живёт подразделами `### Main takeaway` и `### Synthesis` внутри недельной
заметки, со ссылками на источник и на принцип. Парсер вынимает инсайт и оттуда:
запись `## YYYY-MM-DD — заголовок` в `Weekly/` даёт дату, заголовок и подразделы,
из которых `Main takeaway`, `Synthesis` и `Application` отображаются на `insights` и
`applications`. Отдельные файлы в `Insights/` остаются вторым, равноправным путём.

Парсер двухрежимный. Есть frontmatter — читает его. Нет — выводит тип из пути
(`Sources/` → source, `Weekly/` → weekly, `Topics/` → principle) и читает буллеты
вида `- **Status:** Inbox` **только на чтение**, ничего не переписывая. Так работают
все семь существующих заметок до миграции и любые заметки, созданные рукой после.

### Структура vault

Существующая структура сохраняется:

```
Education/Professional Growth/
  Dashboard.md
  Inbox.md              ← сохраняется; список живёт между маркерами и
                          перегенерируется, остальной текст не трогается
  Sources/              ← элемент бэклога = заметка здесь, с frontmatter
  Topics/               ← Professional Principles.md, Design Under Uncertainty.md
  Weekly/               ← сессии дописываются сюда
  Insights/             ← новая папка, создаётся при первой записи
  Working System.md
```

`Design Under Uncertainty.md` и `Professional Principles.md` уже лежат в `Topics/`, а
не в корне. Никуда не переносятся.

Путь к vault хранится в конфиге агента, а не в базе: это свойство машины, а не аккаунта.

## 9. Почему Уровень 0 остаётся на localStorage

Supabase в редакции 2 был вынужден двумя вещами: письмо отправляет сервер, и агенту
нужно место, куда писать. На Уровне 0 нет ни того, ни другого, поэтому база не нужна —
а её включение стоит дороже, чем кажется.

**Отнимает офлайн.** Сейчас всё в `localStorage`, и Полка с Дневником работают в
самолёте. С базой это пропадает; вернуть можно только наполовину — кэшем снимка на
чтение, с честной плашкой «данные от такого-то числа». Полноценная офлайн-очередь
записей — третья система синхронизации в проекте, и она не окупается.

**Замедляет запись.** `DataContext.run()` после любой мутации перезагружает весь
снимок. В `localStorage` это стоило ноль, по сети — сотни миллисекунд на каждое
нажатие, и Полка моргает. Это прямо противоречит требованию «крайне низкое трение»,
на котором держится захват.

**Что из-за этого нельзя откладывать.** Оба лечения — кэш снимка и оптимистичные
мутации общим хелпером — проектируются уже сейчас, но пишутся на Уровне 1. Сейчас
важно другое: **хранилище обучения прячется за интерфейсом `LearningStore` с
реализацией `localLearning`**, ровно по образцу `DataStore` в ядре. Тогда появление
`supabaseLearning` не тронет ни один экран.

**Чего Уровень 0 стоит лишён.** Доступа с телефона и защиты от очистки данных
браузера. Оба лечатся выгрузкой в JSON, которая в Настройках уже есть, и оба
исчезают на Уровне 1.

## 11. Фазы

## 12. Тесты

Правило ядра: интерфейс тестами не покрывается, покрывается то, что ломается тихо.

- `metrics.ts` — `activeWeeks` на границе недели и года, `nextAction` при пустом
  бэклоге, порог режима возврата, агрегаты недели.
- `nextOccurrence` — расчёт ближайшей и пропущенной сессии для блока «Ближайшее»:
  переход на летнее время, воскресенье как день 0, граница суток.
- *(Уровень 2)* догоняющая выборка — переход на летнее время, воскресенье как
  день 0, таймзона профиля против UTC, **пропущенный тик: письмо уходит позже, а не
  теряется**, повторный запуск не шлёт дубль.
- *(Уровень 1)* `markdown.ts` и `diff.ts` агента — парсинг заметок с frontmatter и без, сериализация,
  сравнение по хешу, и **тест, доказывающий, что тело заметки не изменилось после
  записи**. Агент — обычный Node-код, поэтому тесты работают на временной директории
  с настоящими файлами, без браузерных заглушек.
- `store` — те же тесты, что у `local.ts` в ядре: `localLearning` покрывается сразу.

Фикстуры для разбора Markdown — **синтетические, повторяющие форму реальных заметок,
но не содержание**. Бесплатный GitHub Pages требует публичного репозитория, и класть
туда рабочие заметки нельзя. Разбор на настоящем vault проверяется одноразовой пробой
вне репозитория — она уже прогнана 2026-09-20, результат в §13.

|---|---|
| **Агент пишет в папку под управлением iCloud: гонки, конфликтные копии, постоянная выгрузка 2.1 ГБ** | Не удалять ничего; атомарный `rename` из `~/.local/state`; стоп при конфликтной копии; читать часто, писать не чаще раза в сутки и только по изменению. §8 «Работа под iCloud» |
| **У vault нет истории — ошибка агента необратима** | Резервная копия каждого файла до первого изменения, **вне iCloud**. Копия, синхронизируемая вместе с оригиналом, от плохой записи не спасает |
| **iCloud разносит удаление на все устройства** | Агент не удаляет файлы в принципе. Удаление живёт только как `deleted_at` в базе |
| **Слепой обход 3114 файлов, из них 2933 чужих в node_modules** | Жёсткий корень из конфига, без выхода наружу, без точечных папок, без симлинков вовне |
| **Выгруженные файлы при «Оптимизировать хранилище»** | `.icloud`-заглушки пропускаются с отметкой, а не материализуются |
| **Агент работает раз в час с полными правами пользователя** | Ноль внешних зависимостей: только стандартная библиотека Node. Ежечасно исполняемый чужой код из npm — отдельный класс риска, и он просто не заводится |
| **macOS ограничивает доступ к `~/Documents`** | Проверка доступа при установке агента с внятной ошибкой вместо пустого результата |
| **Токен на диске уедет в iCloud, если лежит в `~/Documents`** | `~/.config/learning-hub/`, права `600`, вне vault и вне репозитория |
| **Заметки уезжают в облако Supabase** | Принято осознанно. Стоит знать: vault уже в iCloud, то есть «всё только на моей машине» перестало быть верным до и независимо от этого проекта |
| **Публичный репозиторий у бесплатного GitHub Pages** | Фикстуры синтетические, рабочие заметки в репозиторий не попадают. Секреты — только в Secrets репозитория и в секретах Supabase |
| **Приостановленный проект Supabase со временем удаляется** | Выгрузка в JSON раз в месяц; журнал отправок показывает, что проект жив |

### Что остаётся непокрытым

Гонка «iCloud подтянул удалённую версию между проверкой и `rename`» сужается
повторной сверкой непосредственно перед подменой, но не устраняется полностью.
Последствия обратимы за счёт резервных копий, и до Фазы 3 запись не включается вовсе.

Вынос vault из iCloud в обычную локальную папку убрал бы половину этой таблицы.
Решение — оставить в iCloud ради защиты от отказа Mac — принято осознанно.

## 14. Ограничения продукта

Риски для файлов и системы — в §13. Здесь то, чего система не умеет по устройству,
а не по недосмотру.

### На Уровне 0

1. **Система не зовёт.** «Ближайшее / Пропущено» видно, только когда вы открыли Hub.
   Это прямо оставляет открытой вашу проблему №6 — и это осознанный размен на нулевую
   инфраструктуру. Месяц использования покажет, чего не хватает на самом деле.
2. **Данные в одном браузере.** Очистка данных сайта — потеря всего. Лечится выгрузкой
   в JSON, которая в Настройках уже есть, и исчезает на Уровне 1.
3. **С телефона недоступно.**
4. **Obsidian и Hub не связаны.** Записанное с ChatGPT в vault в Hub не появится.
5. **Два дашборда борются за роль домашней страницы.** Решается после реального
   использования.

### Появляется на Уровне 1

6. **Агент живёт на одном Mac.** Mac выключен — синхронизации нет. Путь к vault
   изменился — агент останавливается молча. Прикрыто `vault_synced_at` и датой
   последней синхронизации в Настройках.
7. **Задержка моста — до часа.** Лечится `npm run sync` вручную.
8. **Правка статуса руками в `Inbox.md` будет затёрта.** Цена одного владельца.
9. **Офлайн возвращается только на чтение.**
10. **Миграция в Supabase одноразовая и необратимая.** Выгрузка в JSON делается до
    неё, не после.

### Появляется на Уровне 2

11. **Точность напоминаний — не лучше получаса**, и GitHub отключает расписание после
    60 дней без активности в репозитории.
12. **Доставляемость писем не гарантирована** с общего домена Resend. Прикрыто
    журналом отправок и детектором молчания, но не устранено.
13. **Email легко проигнорировать** — как календарь и как уведомления ChatGPT.
    Запасной путь дешёвый: `launchd` уже стоит ради синхронизации, и тот же агент
    может показывать системное уведомление macOS, которое нельзя пролистать.

## 15. Чего здесь намеренно нет

- Обращений к языковой модели из приложения. Общий Markdown-слой этого не требует.
- Облачного push и сервис-воркера ради уведомлений: письмо покрывает тот же случай.
- Офлайн-очереди записей.
- Серий по дням и любой геймификации.
- Перестройки чтения под модель потоков.
- Переноса `Design Under Uncertainty.md` и `Professional Principles.md` из `Topics/`.
- Автоматического изменения существующих заметок без подтверждения и диффа.
- File System Access API и любого доступа браузера к файлам: расписания у страницы
  нет, а вторая реализация синхронизации разойдётся с первой.
- Отдельного поля для адреса получателя писем: вход и напоминания — одна почта.
